## Итог в пяти пунктах

1. **Трекер работает одной командой** (`python -m bosona track`) и видит каждую его сделку.
   В прогоне 175 сделок; логи увидели 175, Data API — 175, RTDS — 173. Две сделки RTDS не прислал в первые 15 с после старта нового процесса трекера. Обрывы связи — 14 за прогон — восстанавливались сами за ~1 с.
2. **Основной канал — подписка на on-chain логи** `OrderFilled` (`eth_subscribe` на публичном Polygon RPC).
   Параллельно идёт публичный поток сделок RTDS `activity`. Сделка видна через **2.0 с после матчинга** в CLOB (медиана, p90 3.0 с).
   Кто из двух приходит первым, зависит от часа: за весь прогон логи первыми в 109 сделках, RTDS — в 66. Data API отстаёт от матчинга на 11.3 с (p90 17.0 с), поэтому опрос `/activity` годится только как страховка.
3. **За эти ~2 с спот почти не сдвигается** (Binance сдвинулся лишь в 21% сделок), **а стакан его токена — сдвигается**.
   Лучший ask: p10 −10.0¢, p90 +2.8¢. Он вырос в 24% сделок, упал в 45%.
4. **Копировать его сделки вслепую невыгодно, и дело не в задержке, а в цене входа.**
   - 87% его сделок — maker: он стоит в стакане со своей ценой. Копировщик в момент обнаружения может только забрать ask.
   - На тех же сделках копия хуже его исполнения на **4.2¢ на акцию** (maker-сделки, с весом по объёму, с taker-комиссией).
     Его перевес на maker-сделках за всю историю — **+1.68¢ на акцию** (этап 2). Значит, копия даёт ≈ **−2.5¢ на акцию**.
   - На его 18 taker-сделках копия вышла на 3.1¢ на акцию дешевле него. Выборка мала. На длинной истории эти сделки у него в небольшом плюсе: +0.65¢ на акцию (исправлено 2026-10-02, см. ниже).
   - Вечер был для него убыточным: −17.5¢ на акцию на 156 разрешённых сделках, почти всё — за последние 25 минут.
     Уровень PnL за час ничего не говорит о его перевесе. Значима только разница «копия − оригинал» на одних и тех же сделках.
5. **Chainlink TWAP-60 из RTDS — это ровно то, по чему резолвятся рынки**: на 126 из 126 закрытий значение совпало с официальным `finalPrice`/`priceToBeat` до последнего знака.
   - Binance (USDT) выше Chainlink (USD) на **4.3–5.4 bps** — это базис.
   - Без базиса расхождение TWAP на закрытии — 0.19 bps (p90 0.42), а |движение| за окно — медиана 8.6 bps.
   - Поэтому победитель по Binance совпал с победителем по Chainlink во всех 108 окнах. Там, где официальный итог уже известен, — и с ним.
   - Прокси этапа 2 (Binance, привязанный к strike) ошибается на 0.29 bps (медиана): совпадает с оценкой этапа 2, 0.3–0.9 bps.

## Что сделано

`python -m bosona track` — один asyncio-процесс, всё публичное и только на чтение.
Остановка — Ctrl+C или SIGTERM: трекер дописывает начатые записи, сбрасывает буфер и закрывает сокеты. Выход ~3 с, проверено и на пробном, и на контрольном прогоне.

| Модуль | Что делает |
|---|---|
| `live/detect.py` | три канала обнаружения сделок, у каждого своя метка времени (см. ниже) |
| `live/prices.py` | подключаемые провайдеры цены и «книга цен» с историей за 20 мин |
| `live/books.py` | локальные стаканы из market-канала CLOB, время матчинга по tx hash, цена копирования по стакану |
| `live/markets.py`, `windows.py` | метаданные текущих окон по вычисленному slug: правило сверено со всеми 20 451 рынком с 1 сентября |
| `live/tracker.py` | склейка: снимок в момент обнаружения, сдвиги, Binance vs Chainlink на закрытиях, health раз в минуту |
| `live/outcomes.py` | исходы рынков, где он торговал (Gamma), для PnL |
| `live/store.py`, `live/report.py` | схема `live.db`, команда `live-report` |
| `live/wsconn.py` | общий WebSocket-клиент: переподключение с backoff, heartbeat протокола, пересоздание «молчащих» сокетов |

Тесты: 68 (было 36). Новые проверяют:

- разбор сообщений всех источников;
- одинаковый ключ сделки во всех трёх каналах (на реальной сделке);
- подпись запросов и разбор отчётов Chainlink Data Streams (сверено с официальным SDK);
- стаканы и цену копирования;
- переподключение и «молчащий» сокет на локальном WS-сервере;
- reorg;
- математику отчёта.

## Обнаружение: какой канал и почему

### Три метки времени одной сделки

1. **Матчинг в CLOB** (`match_ms`). Его даёт market-канал CLOB: событие `last_trade_price` несёт `transaction_hash` и время в мс. Это и есть момент сделки.
2. **Блок** (`block_ts`, секунды). Блок с его транзакцией помечен временем через **2.4 с после матчинга** (медиана, p10–p90: 1.6–3.2 с).
   При этом заголовки Polygon приходят на ~1 с **раньше** собственной метки: в отдельной пробе `newHeads` пришли в среднем за 0.9 с до неё.
   Поэтому задержка «от блока» у быстрых каналов отрицательная. Честная точка отсчёта — матчинг.
3. **Обнаружение** (`first_seen_ms`) — наши часы. Они сходятся с серверами: метки CLOB и наш приём расходятся на единицы мс, Binance — на ~35 мс (сеть).

### Каналы

| Канал | Как | Видит | От матчинга, p10 / p50 / p90 | Первым в |
|---|---|---|---|---|
| `chain_logs` | `eth_subscribe` логов `OrderFilled` обеих бирж CLOB V2 с фильтром «maker = его кошелёк», `wss://polygon-bor-rpc.publicnode.com` | 175 из 175 | 1.1 / 2.2 / 3.2 с | 109 |
| `rtds_activity` | RTDS `activity/trades` — поток всех сделок Polymarket (~40/с), фильтр по `proxyWallet` у нас | 173 из 175 | 1.6 / 2.5 / 3.3 с | 66 |
| `data_api` | `/v2/activity?user=…` раз в 3 с | 175 из 175 | 5.1 / 11.3 / 17.0 с | 0 |
| первый из трёх | | | **1.1 / 2.0 / 3.0 с** | |

По запускам контрольного прогона:

| Запуск, UTC | Сделок | Логи первыми | RTDS первым | Медиана от матчинга: логи / RTDS |
|---|---|---|---|---|
| 18:40–18:50 | 16 | 16 | 0 | 1.4 / 2.2 с |
| 18:53–19:35 | 68 | 26 | 42 | 2.5 / 2.5 с |
| 19:35–20:01 | 91 | 67 | 24 | 2.1 / 2.5 с |

До контрольного прогона были две пробы по 7 и 10 минут (`docs/samples/stage3/detection_race.json`).
Опрос RPC раз в 0.4 с проиграл подписке. В пробе с подпиской логи выиграли у RTDS все 9 сделок, а в коротком пробном запуске проиграли 7 из 8.
Скорость публичного RPC плавает, поэтому работают оба канала.

**Выбор: подписка на on-chain события, параллельно — RTDS `activity`, опрос Data API — страховка.**

- **Data API отпадает как основной канал.** API сам отстаёт от блока: медиана 8.8 с, p90 14.3 с (на этапе 0 было ~4 с). Частый опрос этого не исправит: задержка внутри API.
- **On-chain логи ловят все его сделки, и maker, и taker.** Его taker-ордер даёт событие, где maker — он, а taker — адрес биржи.
  Суммы точные, роль и комиссия видны сразу, есть `log_index` и время блока (поле `blockTimestamp`). После обрыва пропуск догружается `eth_getLogs`.
- **RTDS `activity` независим от RPC и включает maker-сделки** (у 63% сообщений потока `fee = 0`).
  Он не помечен как устаревающий: миграционный гайд прямо говорит «Keep using RTDS for the `activity` topic».
- **Market-канал CLOB быстрее всех, но адреса участника в нём нет.** Поэтому он используется для времени матчинга и стаканов, а не для обнаружения.

Каналы склеиваются по ключу `tx:token:side:size_raw:seq`. На реальных сделках ключ совпадает во всех трёх (есть тест).
`seq` у on-chain канала — ранг `log_index` среди одинаковых сделок транзакции. Поэтому сделка, вернувшаяся после reorg в другом блоке, не задвоится.

## Что записывается по каждой сделке

В момент первого обнаружения, синхронно и до любого сетевого запроса, трекер фиксирует:

- последний тик **каждого** источника цены (`binance:spot`, `chainlink:spot`, `chainlink:twap60`);
- стаканы **обоих** токенов рынка из локальной книги market-канала: top-10 уровней, `src = ws`. Такой снимок был у 165 из 175 сделок.

Затем, асинхронно, через ~0.52 с (медиана; p90 0.68 с), — `GET /book` обоих токенов (`src = rest`, у всех сделок) и метаданные рынка, если окно не было загружено заранее.

Через 30 с, когда отчитались медленные каналы (или сразу, если отчитались все три), считаются значения «в момент сделки»:

| Поле `live_fills` | Смысл |
|---|---|
| `ref_ms`, `ref_kind` | время сделки: матчинг CLOB (`match`, 94% сделок); иначе блок минус медиана «блок − матчинг» прогона (`block_est`) |
| `lat_match_ms`, `lat_block_ms` | обнаружение минус матчинг и минус блок |
| `spot_ref`, `spot_detect`, `spot_shift_bps`, `spot_source` | спот источника резолва на момент сделки и на момент обнаружения. Для 5m/15m/4h это Chainlink, пока он жив, иначе Binance; `spot_source` называет, какой из них |
| `bid_ref`/`ask_ref` → `bid_detect`/`ask_detect` | верх стакана его токена перед матчингом и в момент обнаружения |
| `copy_px`, `copy_vwap`, `copy_slip`, `size_at_px` | цена копировщика по стакану в момент обнаружения: лучший ask и VWAP на весь его объём, разница с его ценой, сколько ещё стоит по его цене или лучше |

У каждой цены записан источник: `live_fills.spot_source`, `live_spot_snaps.source/kind`, `live_spot.source/kind`.
Остальные таблицы — в `README.md`.

## Сдвиг цены за задержку

Между матчингом и обнаружением проходит ~2 с. Сдвиг спота меряем по Binance: это свежий источник, тик доходит за ~35 мс.
Chainlink для этого не годится. RTDS доставляет его тик через ~1.4 с после метки, так что в момент обнаружения он показывает цену примерно на момент матчинга.

| Что | p10 | p50 | p90 |
|---|---|---|---|
| спот Binance, \|сдвиг\| от матчинга до обнаружения, bps | 0.00 | 0.00 | 0.83 |
| ask его токена, обнаружение − матчинг, ¢ | −10.0 | 0.0 | +2.8 |
| bid его токена, ¢ | −8.0 | 0.0 | +3.0 |

- **Спот за эти ~2 с почти стоит на месте.** Binance сдвинулся лишь в 21% его сделок (p95 1.17 bps, максимум 3.5 bps).
  Без привязки к его сделкам BTC сдвигается за 2 с в 27% случаев (p90 0.87 bps), за 60 с — медиана 2.4 bps.
  Это обычная среда: минутная волатильность в момент его сделок на этапе 2 — медиана 2.6 bps.
  Связь его входов с движениями спота — тема этапа 4, гипотеза 3.
- **Стакан токена за те же ~2 с двигается на центы.** Двигает его не спот, а сами участники: перекотировки маркет-мейкеров и чужие сделки.
  Лучший ask вырос в 24% сделок и упал в 45%.
  В 35% maker-сделок лучший ask к моменту обнаружения уже **ниже** его цены покупки (медиана разницы −6.0¢).
  Похоже на обычный для maker отбор не в его пользу: его bid исполняют, когда цена токена идёт вниз. Проверим на этапе 4.
  В остальных 63% ask выше его цены, медиана разницы +2.0¢.

## Можно ли копировать

Копия здесь — покупка того же объёма по стакану в момент обнаружения: VWAP по ask плюс taker-комиссия `0.07 × p × (1 − p)`.

| Его роль | Сделок | Его цена, медиана | Лучший ask − его цена, ¢: p10 / p50 / p90 (среднее) | VWAP на его объём − его цена, ¢ (среднее) | Доп. стоимость копии на акцию, ¢: среднее / с весом по объёму |
|---|---|---|---|---|---|
| maker | 153 | 0.44 | −7.2 / +1.0 / +6.0 (−0.8) | −0.5 | +0.7 / +4.3 |
| taker | 22 | 0.59 | −8.8 / −0.2 / +5.8 (−4.0) | −1.4 | −1.3 / −2.9 |

«Доп. стоимость» — (VWAP по стакану − его цена) + комиссия копировщика − комиссия, которую заплатил он (у maker — 0).
Для денег важно взвешенное по объёму значение: крупные сделки проходят по нескольким уровням стакана, и копия обходится дороже.
У мелких сделок ask часто уже ниже его цены, поэтому простое среднее заметно меньше.

**Проверка на исходах.** На 156 сделках прогона с уже известным исходом:

| Его роль | Сделок | Акций | Его PnL, ¢ на акцию | PnL копии, ¢ на акцию | Копия − он |
|---|---|---|---|---|---|
| maker | 138 | 9 079 | −18.6 | −22.8 | −4.2 |
| taker | 18 | 4 378 | −15.3 | −12.2 | +3.1 |
| всего | 156 | 13 457 | −17.5 | −19.3 | −1.8 |

Исход у копии и оригинала один, поэтому разница — это ровно цена копирования на этих сделках. Для maker-сделок она совпадает со взвешенной «доп. стоимостью» выше.

| | Его перевес на акцию (этап 2: вся история / 30 дней) | Доп. стоимость копии (этот прогон, с весом по объёму; минус — копия дешевле) | Ожидание копии на акцию |
|---|---|---|---|
| maker-сделки | +1.68¢ / +1.61¢ | +4.2¢ | **−2.5¢** |
| taker-сделки | +0.65¢ / +0.81¢ | −3.1¢ (мало сделок) | +3.8¢ |

> Исправление 2026-10-02: перевес taker-сделок пересчитан после исправления двойного учёта комиссии на этапе 2 (`docs/stage2-context.md`); было −0.50¢ / −0.47¢ и +2.6¢.
> Maker-сделки не затронуты: комиссии у них нет.

**Вывод.** Задержка в ~2 с сама по себе маржу не съедает: спот за это время почти не двигается. Но копия покупает по рынку то, что он покупает своим лимитным ордером.
На maker-сделках, а это почти весь его оборот, разница в цене больше всего его перевеса. Слепое копирование в минусе.
Цель этапов 4–5 подтверждается: выводить правила (где и когда он ставит лимитные ордера), а не повторять сделки.
Отдельно на этапе 5 стоит проверить копирование его taker-сделок и копию лимитным ордером по его цене. Обе оценки здесь — на малой выборке или без модели исполнения.

## Binance vs Chainlink на закрытии окон

На каждом закрытии 5m/15m/4h по 6 активам трекер пишет в `live_window_close`:

- TWAP-60 Chainlink из RTDS на старте и конце окна (`cl_start`, `cl_end`);
- спот Chainlink и Binance;
- TWAP-60 Binance по 1s-ценам — то же правило, что в прокси этапа 2;
- базис за 10 мин;
- победителя по каждому источнику;
- официальные strike/final/winner из Gamma.

| Что | Значение |
|---|---|
| закрытий записано / с обоими источниками на старте и конце | 138 / 108 |
| `cl_end` = официальный `finalPrice` (и `cl_start` = `priceToBeat`) | **126 из 126, до последнего знака** |
| базис Binance − Chainlink, bps: p10 / p50 / p90 | 4.30 / 4.72 / 5.44 |
| \|расхождение TWAP на закрытии − базис\|, bps: p50 / p90 | 0.19 / 0.42 |
| \|движение Chainlink TWAP за окно\|, bps: p10 / p50 | 2.0 / 8.6 |
| прокси этапа 2 на живых данных, \|ошибка итога\|, bps: p50 / p90 | 0.29 / 0.74 |
| победитель по Binance ≠ победителю по Chainlink (= официальному) | 0 из 108 |

Расхождение важно только тогда, когда окно закрывается у самого strike: |движение| за окно меньше ~0.5 bps.
В прогоне таких окон было 4 из 108; ближайшее — +0.004 bps у BTC 5m в 20:00.
Binance угадал победителя во всех 4, но там запас был меньше расхождения источников. Это везение, а не надёжность.
Для этапов 4–5 это значит: по Binance с поправкой на базис итог окна угадывается почти всегда. Ошибается он только в окнах «на волоске».
Именно они и важны для его поздних входов: это проверим на истории.

Важное наблюдение для схемы резолва: RTDS `crypto_prices_twap_sixty` с меткой времени, равной концу окна, и есть официальный итог.
Если в Gamma ещё нет `finalPrice`, его даёт `priceToBeat` следующего окна.

## Надёжность

- **Переподключение.** У каждого сокета своя петля с backoff 1–60 с и джиттером.
  Если сокет молчит дольше порога, его пересоздают: 30 с для Binance и RTDS, 60 с для market-канала. Для RTDS-цен отдельная проверка: если сокет отвечает только на heartbeat, а тиков нет минуту, его тоже пересоздают. Так будет выглядеть удалённый топик.
  В прогоне сокеты Polymarket рвались 14 раз (RTDS activity — 5, market-канал CLOB — 4, RTDS цены — 4, Binance — 1). Каждый раз они вернулись за ~1 с.
  Ни одна сделка не потерялась: каждую сделку увидели минимум два канала из трёх (пропуски: rtds_activity — 2).
- **Пропуски.** После обрыва логи догружаются `eth_getLogs` с последнего виденного блока, до 2000 блоков (~70 мин). Остальное подхватывает Data API.
- **Источники цены независимы.** Если Chainlink перестанет приходить, в снимках он будет помечен устаревшим (`det_age_ms`), и «главным» спотом станет Binance.
  Раз в минуту в лог пишется предупреждение; трекер не падает. Упавший компонент логируется и перезапускается через 5 с.
- **Закрытие окна ждёт свой тик.** Сверка с официальными итогами нашла ошибку.
  В 6 закрытиях в 19:50 RTDS прислал тик последней секунды окна позже 3-секундной паузы. Трекер взял значение предыдущей секунды, и расхождение составило 0.01–0.1 bps.
  Исправлено: трекер ждёт тик последней секунды окна, до 15 с. Эти 6 записей пересчитаны из посекундной истории `live_spot`.
- **Остановка.** Найдено и исправлено зависание при остановке.
  На Python 3.11 `asyncio.wait_for` на нагруженном сокете иногда «съедал» отмену, и процесс не выходил по SIGTERM. Теперь используется `asyncio.timeout`.
- **Логи.** `logs/live.log` с ротацией (20 МБ × 10).
  На каждую сделку — две строки: обнаружение и итог с задержками, сдвигами и ценой копии. На каждое закрытие окна — строка Binance vs Chainlink. Раз в минуту — health; он же пишется в `live_health`.
- **Нагрузка.** ~13% CPU, память ~100 МБ на старте и 130–150 МБ через 20–40 минут: рост замедляется, когда заполнены 20-минутные буферы; многодневный прогон ещё не проверен.
  `live.db` растёт на ~120–130 МБ в сутки; две трети объёма — посекундные цены.
  Market-канал CLOB тяжёлый: одно окно BTC даёт ~60 обновлений стакана в секунду. На ~12 рынках сразу сервер закрыл соединение с кодом 1013 «slow consumer».
  Поэтому стакан стримится только для серий, где ~88% его сделок: BTC 5m/15m/1h и ETH 5m. Ещё 15 минут стримится любой рынок, где он только что торговал. Остальное снимается REST `/book` в момент обнаружения.

## Сомнения и ограничения

- **Выборка — 1.3 ч трекинга одного вечера (три запуска).** Задержки и расхождения источников уже устойчивы, а PnL на ~156 сделках — нет.
  Это иллюстрация механики. Вывод о копировании опирается на перевес из всей истории (этап 2) и на стоимость копии из прогона. Полный расчёт — этап 5.
- **Копия здесь — мгновенная покупка по стакану в момент обнаружения.** Не учтены наша задержка отправки, taker delay биржи (150 мс на крипте с 2026-09-04) и сдвиг стакана за это время.
  Оценка оптимистична. Вариант «поставить свой maker-ордер по его цене» здесь не оценивается: нужна модель очереди (этап 5).
- **Публичный RPC** `polygon-bor-rpc.publicnode.com` бесплатный и без SLA. Задержка зависит от его ноды, поэтому каналов два. Свой нод или платный RPC дал бы стабильнее.
- **Время матчинга есть только у рынков из стрима** — 94% сделок. У остальных время сделки оценивается как «блок минус медиана» с точностью около ±0.5 с.
- **Chainlink из RTDS — до ~2026-10-23.** После удаления топиков трекер продолжит работать на Binance с базисом.
  Официальный итог окна по-прежнему придёт из Gamma через 1–5 мин.
  Провайдер Chainlink Data Streams готов, но вживую не проверен: нет ключа, а хосты `api.dataengine.chain.link` и `ws.dataengine.chain.link` из контейнера закрыты (403).
  Подпись запросов и разбор отчётов сверены с официальным SDK `@chainlink/data-streams-sdk` 1.3.0.
  Feed id известен только для BTC/USD spot (пример из SDK). Id TWAP-стримов, по которым идёт резолв (`btc-usd-twap-60s-streams`), нужно взять на data.chain.link.
- **У Gamma три особенности**, найденные по ходу. Резолвер их учитывает и повторяет запросы.
  - Ответы кэшируются на CDN до 5 минут: свежезакрытый рынок может несколько минут «не находиться».
  - `/markets` без `limit` отдаёт максимум 20 строк.
  - `finalPrice` появляется позже победителя.
- **Data API стал медленнее**: медиана 8.8 с от блока против ~4 с на этапе 0. Для истории это не важно, для live — только страховка.

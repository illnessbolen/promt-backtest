## Итог в пяти пунктах

1. **Трекер работает одной командой** (`python -m bosona track`) и видит каждую его сделку.
   В прогоне 89 сделок; логи увидели 89, Data API — 89, RTDS — 87. Две сделки RTDS не прислал в первые 15 с после старта нового процесса трекера. Обрывы связи — 11 за прогон — восстанавливались сами за ~1 с.
2. **Основной канал — подписка на on-chain логи** `OrderFilled` (`eth_subscribe` на публичном Polygon RPC).
   Параллельно идёт публичный поток сделок RTDS `activity`. Сделка видна через **2.1 с после матчинга** в CLOB (медиана, p90 3.1 с).
   Два канала финишируют вровень: логи первыми в 46 сделках, RTDS — в 43. Data API отстаёт на 10.2 с (p90 16.9 с), поэтому опрос `/activity` годится только как страховка.
3. **За эти ~2 с спот почти не сдвигается** (Binance сдвинулся лишь в 10% сделок), **а стакан его токена — сдвигается**.
   Лучший ask: p10 −7.0¢, p90 +2.0¢. Он вырос в 25% сделок, упал в 34%.
4. **Копирование проигрывает не на задержке, а на роли.**
   - 87% его сделок — maker: он покупает по своему bid. Копировщик в момент обнаружения может только забрать ask.
   - Это стоит в среднем **+3.0¢ на акцию** сверх его цены, включая taker-комиссию; с весом по объёму — +5.8¢.
   - Его собственный перевес на maker-сделках за всю историю — **+1.68¢ на акцию** (этап 2). Ожидание копии: **−1.4¢ на акцию**.
   - Сделки прогона с уже известным исходом (69): у него +$194 (+5.7% к вложенному), у копировщика −$110 (−3.0%).
5. **Chainlink TWAP-60 из RTDS — это ровно то, по чему резолвятся рынки**: на 72 из 72 закрытий значение совпало с официальным `finalPrice`/`priceToBeat` до последнего знака.
   - Binance (USDT) выше Chainlink (USD) на **4.3–5.0 bps** — это базис.
   - Без базиса расхождение TWAP на закрытии — 0.20 bps (p90 0.40), а |движение| за окно — медиана 9.4 bps.
   - Поэтому победитель по Binance совпал с победителем по Chainlink во всех 72 окнах. Там, где официальный итог уже известен, — и с ним.
   - Прокси этапа 2 (Binance, привязанный к strike) ошибается на 0.29 bps (медиана): совпадает с оценкой этапа 2, 0.3–0.9 bps.

## Что сделано

`python -m bosona track` — один asyncio-процесс, всё публичное и только на чтение.
Остановка — Ctrl+C или SIGTERM: трекер дописывает начатые записи, сбрасывает буфер и закрывает сокеты. Выход ~3 с, проверено и на пробном, и на контрольном прогоне.

| Модуль | Что делает |
|---|---|
| `live/detect.py` | три канала обнаружения сделок, у каждого своя метка времени (см. ниже) |
| `live/prices.py` | подключаемые провайдеры цены и «книга цен» с историей за 20 мин |
| `live/books.py` | локальные стаканы из market-канала CLOB, время матчинга по tx hash, цена копирования по стакану |
| `live/markets.py`, `windows.py` | метаданные текущих окон по вычисленному slug: правило сверено со всеми 20 451 рынком с 1 сентября |
| `live/tracker.py` | склейка: снимок в момент обнаружения, сдвиги, Binance vs Chainlink на закрытиях, health раз в минуту |
| `live/outcomes.py` | исходы рынков, где он торговал (Gamma), для PnL |
| `live/store.py`, `live/report.py` | схема `live.db`, команда `live-report` |
| `live/wsconn.py` | общий WebSocket-клиент: переподключение с backoff, heartbeat протокола, пересоздание «молчащих» сокетов |

Тесты: 66 (было 36). Новые проверяют:

- разбор сообщений всех источников;
- одинаковый ключ сделки во всех трёх каналах (на реальной сделке);
- подпись запросов и разбор отчётов Chainlink Data Streams (сверено с официальным SDK);
- стаканы и цену копирования;
- переподключение и «молчащий» сокет на локальном WS-сервере;
- reorg;
- математику отчёта.

## Обнаружение: какой канал и почему

### Три метки времени одной сделки

1. **Матчинг в CLOB** (`match_ms`). Его даёт market-канал CLOB: событие `last_trade_price` несёт `transaction_hash` и время в мс. Это и есть момент сделки.
2. **Блок** (`block_ts`, секунды). Блок с его транзакцией помечен временем через **2.5 с после матчинга** (медиана, p10–p90: 1.7–3.2 с).
   При этом заголовки Polygon приходят на ~1 с **раньше** собственной метки: в отдельной пробе `newHeads` пришли в среднем за 0.9 с до неё.
   Поэтому задержка «от блока» у быстрых каналов отрицательная. Честная точка отсчёта — матчинг.
3. **Обнаружение** (`first_seen_ms`) — наши часы. Они сходятся с серверами: метки CLOB и наш приём расходятся на единицы мс, Binance — на ~35 мс (сеть).

### Каналы

| Канал | Как | Видит | От матчинга, p10 / p50 / p90 | Первым в |
|---|---|---|---|---|
| `chain_logs` | `eth_subscribe` логов `OrderFilled` обеих бирж CLOB V2 с фильтром «maker = его кошелёк», `wss://polygon-bor-rpc.publicnode.com` | 89 из 89 | 1.0 / 2.2 / 3.4 с | 46 |
| `rtds_activity` | RTDS `activity/trades` — поток всех сделок Polymarket (~40/с), фильтр по `proxyWallet` у нас | 87 из 89 | 1.5 / 2.4 / 3.2 с | 43 |
| `data_api` | `/v2/activity?user=…` раз в 3 с | 89 из 89 | 5.4 / 10.2 / 16.9 с | 0 |
| первый из трёх | | | **1.0 / 2.1 / 3.1 с** | |

До контрольного прогона были две пробы по 7 и 10 минут (`docs/samples/stage3/detection_race.json`).
Опрос RPC раз в 0.4 с проиграл подписке. В пробе с подпиской логи выиграли у RTDS все 9 сделок, а в коротком пробном запуске проиграли 7 из 8.
Скорость публичного RPC плавает, поэтому работают оба канала.

**Выбор: подписка на on-chain события, параллельно — RTDS `activity`, опрос Data API — страховка.**

- **Data API отпадает как основной канал.** API сам отстаёт от блока: медиана 7.9 с, p90 13.7 с (на этапе 0 было ~4 с). Частый опрос этого не исправит: задержка внутри API.
- **On-chain логи ловят все его сделки, и maker, и taker.** Его taker-ордер даёт событие, где maker — он, а taker — адрес биржи.
  Суммы точные, роль и комиссия видны сразу, есть `log_index` и время блока (поле `blockTimestamp`). После обрыва пропуск догружается `eth_getLogs`.
- **RTDS `activity` независим от RPC и включает maker-сделки** (у 63% сообщений потока `fee = 0`).
  Он не помечен как устаревающий: миграционный гайд прямо говорит «Keep using RTDS for the `activity` topic».
- **Market-канал CLOB быстрее всех, но адреса участника в нём нет.** Поэтому он используется для времени матчинга и стаканов, а не для обнаружения.

Каналы склеиваются по ключу `tx:token:side:size_raw:seq`. На реальных сделках ключ совпадает во всех трёх (есть тест).
`seq` у on-chain канала — ранг `log_index` среди одинаковых сделок транзакции. Поэтому сделка, вернувшаяся после reorg в другом блоке, не задвоится.

## Что записывается по каждой сделке

В момент первого обнаружения, синхронно и до любого сетевого запроса, трекер фиксирует:

- последний тик **каждого** источника цены (`binance:spot`, `chainlink:spot`, `chainlink:twap60`);
- стаканы **обоих** токенов рынка из локальной книги market-канала: top-10 уровней, `src = ws`. Такой снимок был у 83 из 89 сделок.

Затем, асинхронно, через ~0.52 с (медиана; p90 0.63 с), — `GET /book` обоих токенов (`src = rest`, у всех сделок) и метаданные рынка, если окно не было загружено заранее.

Через 30 с, когда отчитались медленные каналы (или сразу, если отчитались все три), считаются значения «в момент сделки»:

| Поле `live_fills` | Смысл |
|---|---|
| `ref_ms`, `ref_kind` | время сделки: матчинг CLOB (`match`, 93% сделок); иначе блок минус медиана «блок − матчинг» прогона (`block_est`) |
| `lat_match_ms`, `lat_block_ms` | обнаружение минус матчинг и минус блок |
| `spot_ref`, `spot_detect`, `spot_shift_bps`, `spot_source` | спот источника резолва на момент сделки и на момент обнаружения. Для 5m/15m/4h это Chainlink, пока он жив, иначе Binance; `spot_source` называет, какой из них |
| `bid_ref`/`ask_ref` → `bid_detect`/`ask_detect` | верх стакана его токена перед матчингом и в момент обнаружения |
| `copy_px`, `copy_vwap`, `copy_slip`, `size_at_px` | цена копировщика по стакану в момент обнаружения: лучший ask и VWAP на весь его объём, разница с его ценой, сколько ещё стоит по его цене или лучше |

У каждой цены записан источник: `live_fills.spot_source`, `live_spot_snaps.source/kind`, `live_spot.source/kind`.
Остальные таблицы — в `README.md`.

## Сдвиг цены за задержку

Между матчингом и обнаружением проходит ~2 с. Сдвиг спота меряем по Binance: это свежий источник, тик доходит за ~35 мс.
Chainlink для этого не годится. RTDS доставляет его тик через ~1.4 с после метки, так что в момент обнаружения он показывает цену примерно на момент матчинга.

| Что | p10 | p50 | p90 |
|---|---|---|---|
| спот Binance, \|сдвиг\| от матчинга до обнаружения, bps | 0.00 | 0.00 | 0.00 |
| ask его токена, обнаружение − матчинг, ¢ | −7.0 | 0.0 | +2.0 |
| bid его токена, ¢ | −7.0 | 0.0 | +2.8 |

- **Спот за эти ~2 с почти стоит на месте.** Binance сдвинулся лишь в 10% его сделок (p95 0.73 bps, максимум 2.1 bps).
  Без привязки к его сделкам BTC сдвигается за 2 с в 27% случаев (p90 0.91 bps), за 60 с — медиана 2.4 bps.
  Это обычная среда: минутная волатильность в момент его сделок на этапе 2 — медиана 2.6 bps.
  Его сделки, похоже, приходятся на спокойные секунды. Это материал для этапа 4: гипотезы 3 (опережение по споту) и 4 (маркет-мейкинг).
- **Стакан токена за те же ~2 с двигается на центы.** Двигает его не спот, а сами участники: перекотировки маркет-мейкеров и чужие сделки.
  Лучший ask вырос в 25% сделок и упал в 34%.
  В 21% maker-сделок лучший ask к моменту обнаружения уже **ниже** его цены покупки (медиана разницы −6.0¢). Это обычный для maker отбор не в его пользу: его bid исполняют, когда цена идёт вниз.
  В остальных 79% ask выше его цены, медиана разницы +1.0¢.

## Можно ли копировать

| Его роль | Сделок | Его цена, медиана | Лучший ask − его цена, ¢: p10 / p50 / p90 (среднее) | VWAP на его объём − его цена, ¢ (среднее) | Доп. стоимость на акцию с комиссией, ¢: среднее / с весом по объёму |
|---|---|---|---|---|---|
| maker | 77 | 0.35 | −6.0 / +1.0 / +5.0 (+1.4) | +2.0 | **+3.0 / +5.8** |
| taker | 12 | 0.54 | −2.9 / 0.0 / +3.6 (+0.1) | +0.3 | +0.3 / −0.7 |

«Доп. стоимость» — сколько копировщик платит на акцию сверх него:
(VWAP по стакану − его цена) + taker-комиссия копировщика `0.07 × p × (1 − p)` − комиссия, которую заплатил он (у maker — 0).
Исход рынка у копии и оригинала один и тот же. Поэтому ожидание копии на акцию = его перевес − доп. стоимость.

| | Его перевес на акцию (этап 2, вся история / 30 дней) | Доп. стоимость копии (этот прогон) | Ожидание копии на акцию |
|---|---|---|---|
| maker-сделки | +1.68¢ / +1.61¢ | +3.0¢ | **−1.4¢** |
| taker-сделки | −0.50¢ / −0.47¢ | +0.3¢ | **−0.8¢** |

Проверка на сделках прогона с уже известным исходом:


| Его роль | Сделок | Его PnL | PnL копии |
|---|---|---|---|
| maker | 59 | +$154 | −$164 |
| taker | 10 | +$40 | +$55 |
| всего | 69 | +$194 (+5.7%) | −$110 (−3.0%) |

Знак и размер здесь определяют несколько крупных сделок, поэтому смотреть надо на разницу между столбцами, а не на уровень.

**Вывод.** Задержка в ~2 с сама по себе маржу не съедает: спот за это время почти не двигается.
Но слепое копирование всё равно в минусе: он зарабатывает как maker, а копия по рынку — это taker.
Копировщик платит спред и комиссию (~2.7¢ на акцию в среднем), а его перевес на maker-сделках — ~1.7¢.
Копировать его taker-сделки можно почти без потерь, но они и у него в минусе на длинной истории (−0.5¢ на акцию).
Поэтому цель этапов 4–5 подтверждается: выводить правила — когда и где он ставит maker-ордера, — а не повторять сделки.

## Binance vs Chainlink на закрытии окон

На каждом закрытии 5m/15m/4h по 6 активам трекер пишет в `live_window_close`:

- TWAP-60 Chainlink из RTDS на старте и конце окна (`cl_start`, `cl_end`);
- спот Chainlink и Binance;
- TWAP-60 Binance по 1s-ценам — то же правило, что в прокси этапа 2;
- базис за 10 мин;
- победителя по каждому источнику;
- официальные strike/final/winner из Gamma.

| Что | Значение |
|---|---|
| закрытий записано / с обоими источниками на старте и конце | 96 / 72 |
| `cl_end` = официальный `finalPrice` (и `cl_start` = `priceToBeat`) | **72 из 72, до последнего знака** |
| базис Binance − Chainlink, bps: p10 / p50 / p90 | 4.28 / 4.61 / 5.03 |
| \|расхождение TWAP на закрытии − базис\|, bps: p50 / p90 | 0.20 / 0.40 |
| \|движение Chainlink TWAP за окно\|, bps: p10 / p50 | 2.4 / 9.4 |
| прокси этапа 2 на живых данных, \|ошибка итога\|, bps: p50 / p90 | 0.29 / 0.69 |
| победитель по Binance ≠ победителю по Chainlink (= официальному) | 0 из 72 |

Расхождение важно только тогда, когда окно закрывается у самого strike: |движение| за окно меньше ~0.5 bps.
В прогоне таких окон не было, ближайшее — 0.24 bps.
Для этапов 4–5 это значит: по Binance с поправкой на базис итог окна угадывается почти всегда. Ошибается он только в окнах «на волоске».
Именно они и важны для его поздних входов: это проверим на истории.

Важное наблюдение для схемы резолва: RTDS `crypto_prices_twap_sixty` с меткой времени, равной концу окна, и есть официальный итог.
Если в Gamma ещё нет `finalPrice`, его даёт `priceToBeat` следующего окна.

## Надёжность

- **Переподключение.** У каждого сокета своя петля с backoff 1–60 с и джиттером.
  Если сокет молчит дольше порога, его пересоздают: 30 с для Binance и RTDS, 60 с для market-канала. Для RTDS-цен отдельная проверка: если сокет отвечает только на heartbeat, а тиков нет минуту, его тоже пересоздают. Так будет выглядеть удалённый топик.
  В прогоне сокеты Polymarket рвались 11 раз (RTDS activity — 4, RTDS цены — 4, market-канал CLOB — 3). Каждый раз они вернулись за ~1 с.
  Ни одна сделка не потерялась: каждую сделку увидели минимум два канала из трёх (пропуски: rtds_activity — 2).
- **Пропуски.** После обрыва логи догружаются `eth_getLogs` с последнего виденного блока, до 2000 блоков (~70 мин). Остальное подхватывает Data API.
- **Источники цены независимы.** Если Chainlink перестанет приходить, в снимках он будет помечен устаревшим (`det_age_ms`), и «главным» спотом станет Binance.
  Раз в минуту в лог пишется предупреждение; трекер не падает. Упавший компонент логируется и перезапускается через 5 с.
- **Остановка.** Найдено и исправлено зависание при остановке.
  На Python 3.11 `asyncio.wait_for` на нагруженном сокете иногда «съедал» отмену, и процесс не выходил по SIGTERM. Теперь используется `asyncio.timeout`.
- **Логи.** `logs/live.log` с ротацией (20 МБ × 10).
  На каждую сделку — две строки: обнаружение и итог с задержками, сдвигами и ценой копии. На каждое закрытие окна — строка Binance vs Chainlink. Раз в минуту — health; он же пишется в `live_health`.
- **Нагрузка.** 12–18% CPU, память 95–150 МБ.
  `live.db` растёт на ~120–130 МБ в сутки; две трети объёма — посекундные цены.
  Market-канал CLOB тяжёлый: одно окно BTC даёт ~60 обновлений стакана в секунду. На ~12 рынках сразу сервер закрыл соединение с кодом 1013 «slow consumer».
  Поэтому стакан стримится только для серий, где ~88% его сделок: BTC 5m/15m/1h и ETH 5m. Ещё 15 минут стримится любой рынок, где он только что торговал. Остальное снимается REST `/book` в момент обнаружения.

## Сомнения и ограничения

- **Выборка — 1.1 ч трекинга одного вечера (три запуска).** Задержки и расхождения источников уже устойчивы, а PnL на ~69 сделках — нет.
  Это иллюстрация механики. Вывод о копировании опирается на перевес из всей истории (этап 2) и на стоимость копии из прогона. Полный расчёт — этап 5.
- **Копия здесь — мгновенная покупка по стакану в момент обнаружения.** Не учтены наша задержка отправки, taker delay биржи (150 мс на крипте с 2026-09-04) и сдвиг стакана за это время.
  Оценка оптимистична. Вариант «поставить свой maker-ордер по его цене» здесь не оценивается: нужна модель очереди (этап 5).
- **Публичный RPC** `polygon-bor-rpc.publicnode.com` бесплатный и без SLA. Задержка зависит от его ноды, поэтому каналов два. Свой нод или платный RPC дал бы стабильнее.
- **Время матчинга есть только у рынков из стрима** — 93% сделок. У остальных время сделки оценивается как «блок минус медиана» с точностью около ±0.5 с.

# bosona-tracker

Сбор и разбор сделок трейдера Polymarket @bosona, чтобы понять его стратегию и подготовить основу для бота с бэктестами.

Ты работаешь как senior Python-разработчик и квант-аналитик.

## Объект

- Трейдер: @bosona
- Кошелёк (proxy wallet): `0xc2ad03f79ca3f3c17d8c7de2612ce0c89b7d40ed`
- Профиль: https://polymarket.com/@bosona

Предварительные наблюдения (проверь на данных, не принимай на веру):
- торгует почти только крипторынки Up/Down: BTC, ETH, SOL, XRP, DOGE, BNB; окна 5m, 15m, 1h и дневные;
- с мая 2026 ~89.6K сделок, объём ~$20.6M, PnL ~+$347K → ~1.7% от оборота, похоже на автоматизированного бота;
- часто держит ОБЕ стороны (Up и Down) одного рынка одновременно, иногда с суммарной ценой пары < $1.

Цель — не слепое копирование (задержка съест маржу), а понять ПРАВИЛА: когда он входит, по какой цене, каким размером, с какой стороны, maker он или taker, и воспроизводимо ли это бэктестом.

## Жёсткие ограничения

- Только чтение. Никаких ордеров, приватных ключей и подключения кошелька.
- Только публичные источники: Data API (`data-api.polymarket.com`), Gamma API (`gamma-api.polymarket.com`), публичная часть CLOB API (`clob.polymarket.com`), Binance public REST/WebSocket, при необходимости публичный Polygon RPC.
- Не выдумывай эндпоинты и поля. Перед написанием кода делай тестовые запросы, показывай реальные примеры ответов и сверяйся с docs.polymarket.com.
- Соблюдай rate limits: backoff, кеширование, умеренный параллелизм.

## Этапы

### Этап 0 — разведка (сделай только это и остановись)
1. Запроси `/activity`, `/trades`, `/positions` и закрытые позиции (если такой эндпоинт есть) для этого user. Покажи структуру ответов, типы активности (TRADE, MERGE, REDEEM, SPLIT и т.п.), точность таймстемпов.
2. Выясни лимиты пагинации: можно ли выкачать всю историю (~90K сделок). Если Data API упирается в лимит — предложи запасной источник (события OrderFilled контрактов CTF Exchange на Polygon или публичный subgraph).
3. Через Gamma API выясни, как по slug/conditionId получить метаданные рынка: начало/конец окна, token id для Up и Down, правила разрешения (какой источник цены и какая «цена открытия» используются для 5m/15m/1h/дневных рынков — они могут отличаться).
4. Узнай текущую схему комиссий для этих рынков.

Выдай короткий отчёт + предложение схемы БД. Дальше не иди, пока я не подтвержу.

### Этап 1 — выгрузка истории
- Вся доступная история в SQLite (`data/bosona.db`). Идемпотентно: повторный запуск докачивает только новое. Надёжный ключ дедупликации (tx hash + log index / asset + side + size).
- Таблицы примерно: `trades`, `activity` (merge/redeem/split), `markets`, `resolutions`, `market_context`.
- По каждой сделке: ts (максимальная точность), conditionId, slug, asset (token id), outcome (Up/Down), side, price, size, usdc_value, tx_hash, роль maker/taker (если определима, например on-chain).

### Этап 2 — обогащение контекстом (ключевое для бэктестов)
Для каждой сделки посчитай и сохрани:
- актив и таймфрейм рынка; секунды от открытия окна и до закрытия;
- «цену открытия» окна (strike) и спот-цену в момент сделки (по тому источнику, по которому резолвится рынок, иначе Binance 1s klines); расстояние до strike в bps;
- волатильность спота за 1/5/15 минут до сделки;
- если доступно: цены/стакан обоих токенов около момента сделки (prices-history, best bid/ask, спред);
- исход рынка и итоговый PnL позиции.

### Этап 3 — live-трекер
- Отдельный процесс, ловящий новые сделки почти в реальном времени: опрос `/activity` каждые 2–5 с или подписка на on-chain события по адресу. Выбери вариант и обоснуй.
- На каждую новую сделку записывай её + снимок стакана обоих токенов + спот-цену в момент ОБНАРУЖЕНИЯ.
- Логируй задержку обнаружения (время сделки/блока vs время, когда мы её увидели) и сдвиг цены за эту задержку. Это ответ на вопрос, можно ли вообще копировать.
- Надёжность: автопереподключение, логи в `logs/`, запуск одной командой, корректное завершение.

### Этап 4 — разбор стратегии (notebook или скрипт с отчётом в markdown)
Сгруппируй сделки в «эпизоды» по conditionId и проверь гипотезы:
1. **Парная торговля**: покупает Up и Down так, что средняя цена пары < $1, потом merge или держит до резолва? Распределение цены пары, доля полностью захеджированных эпизодов, остаточная направленная экспозиция.
2. **Поздние входы с высокой вероятностью**: покупки по 90–99¢ ближе к концу окна. Реальный EV с учётом редких проигрышей.
3. **Опережение по споту**: входит ли он сразу после резкого движения на бирже, пока Polymarket не переоценился? Посчитай лаг между движением спота и его сделками.
4. **Market making**: признаки maker-роли, много мелких сделок с обеих сторон около mid.

Для каждого сегмента (актив × таймфрейм × ценовой бакет × время до закрытия): число сделок, винрейт, средний вход, EV на $1, суммарный PnL, макс. просадка. Прибыльность оценивай через EV, а не через винрейт — высокий винрейт на входах по 95¢ может давать минус.

### Этап 5 — основа для бэктеста
- Сформулируй найденные правила как явные условия входа, выхода и размера позиции.
- Бэктест-движок, проигрывающий историю рынков с реалистичным исполнением: наша задержка, спред, проскальзывание, комиссии, минимальный размер ордера, ограниченная ликвидность стакана.
- Сравни: (a) идеальное копирование его сделок, (b) копирование с измеренной нами задержкой, (c) собственная стратегия по выведенным правилам.
- Архитектура стратегии должна позволять подключить её к моему существующему боту updown-bot (режим DRY_RUN, профили риска conservative/moderate/aggressive) или запустить отдельно.
